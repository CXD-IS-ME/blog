服务注册与发现：Consul 实践

服务注册与发现：Consul 实践

引言

在微服务架构中，服务实例的数量和位置是动态变化的。服务注册与发现机制让服务能够自动感知彼此的存在，无需硬编码 IP 地址。Consul 是 HashiCorp 推出的分布式服务发现和配置管理工具，支持健康检查、KV 存储和多数据中心。

知识点概览

1. 服务注册

服务启动时向 Consul 注册自身信息（IP、端口、健康检查端点），服务关闭时主动注销。

2. 服务发现

通过 Consul API 或 DNS 查询可用服务实例列表，支持负载均衡和故障转移。

3. 健康检查

Consul 定期探测服务健康状态，自动摘除不健康的实例，保证调用方只获取可用节点。

4. KV 配置存储

Consul 内置 KV 存储，可用于动态配置管理，支持 Watch 机制监听配置变更。

小结

本文介绍了基于 Consul 的服务注册与发现实践：

  • 服务启动时自动注册到 Consul，关闭时主动注销
  • Consul 通过健康检查自动摘除不健康实例
  • 客户端通过 Consul 发现可用服务实例，支持随机负载均衡
  • Consul KV 存储可用于动态配置管理
  • 结合 gRPC 实现服务间动态调用

微服务通信基础：RESTful API 与 gRPC

微服务通信基础：RESTful API 与 gRPC

引言

微服务之间需要高效可靠的通信机制。RESTful API 是最广泛使用的同步通信方式，而 gRPC 凭借 Protocol Buffers 和 HTTP/2 在性能上具有显著优势。本文将对比这两种通信方式，并给出 Go 语言的实践示例。

知识点概览

1. RESTful API 通信

基于 HTTP 协议，使用 JSON 格式，简单通用，跨语言兼容性好，适合对外 API 和服务间简单调用。

2. Protocol Buffers 定义

使用 .proto 文件定义服务接口和消息结构，强类型、跨语言，编译生成客户端和服务端代码。

3. gRPC 四种调用模式

一元 RPC、服务端流式、客户端流式、双向流式，覆盖不同通信场景。

4. 通信选型建议

内部服务间高性能通信首选 gRPC，对外 API 和对前端通信使用 RESTful。

  • RESTful API 简单通用，适合对外接口和前端通信
  • gRPC 基于 Protobuf 和 HTTP/2，性能优越，适合内部服务间调用
  • proto 文件作为服务契约，自动生成客户端和服务端代码
  • 实际项目中可以将两者结合，对外用 REST，对内用 gRPC
  • gRPC 支持四种调用模式，满足不同场景需求

微服务架构概述：从单体到微服务的演进

微服务架构概述：从单体到微服务的演进

引言

随着业务规模的增长，传统的单体架构逐渐暴露出部署缓慢、扩展困难、技术栈锁定等问题。微服务架构通过将大型应用拆分为一组小型、自治的服务，成为现代后端开发的主流范式。本文将介绍微服务架构的核心概念、演进历程以及与传统单体架构的对比。

知识点概览

1. 单体架构的局限性

单体架构将所有功能模块打包在一个进程中，初期开发效率高，但随着系统膨胀，耦合严重、部署周期长、团队协作冲突等问题日益突出。

2. 微服务的核心原则

微服务围绕业务能力组织，每个服务独立部署、独立扩展，拥有自己的数据存储，通过轻量级通信机制协作。

3. 服务拆分策略

按照业务领域（DDD 限界上下文）拆分，遵循高内聚低耦合原则，确保每个服务职责单一。

4. 微服务面临的挑战

分布式系统的固有复杂性：网络延迟、数据一致性、服务治理、运维监控等。

  • 微服务通过按业务拆分实现独立部署和独立扩展
  • 每个微服务拥有独立数据库，通过轻量级通信协作
  • 微服务带来了分布式系统的复杂性，需要配套的服务治理基础设施
